PINGBOARD — PROJECT HANDOVER
Multi-tenant uptime monitoring with public status pages
Built 2026-09-29 to 2026-10-05 · Phases 0-7 complete, Phase 8 not started
================================================================================

If you only read one section, read "HOW TO RUN IT" and "GOTCHAS". Everything
else is context.


--------------------------------------------------------------------------------
1. WHAT IT IS
--------------------------------------------------------------------------------

An organisation signs up, registers monitors (a URL + check interval + a set of
assertions), and a background worker checks them on schedule. Failures open
incidents automatically and notify the team over Slack / Discord / email. Each
org can publish a public status page that anyone can view without logging in.

Think a small, self-hostable UptimeRobot / Better Uptime.

Stack:
  Backend    FastAPI (fully async), SQLAlchemy 2.1, Alembic, Pydantic v2
  Worker     ARQ (Redis-backed, async-native)
  Database   PostgreSQL 16
  Cache/Queue Redis 7
  Frontend   React 19 + TypeScript + Vite 7 + Tailwind v4 + TanStack Query
  Charts     Recharts
  Infra      Docker Compose (5 services)

Size: ~5,700 lines backend app, ~4,300 lines frontend, ~1,000 lines tests.
41 API operations across 32 paths. 6 migrations. 215 tests.


--------------------------------------------------------------------------------
2. HOW TO RUN IT
--------------------------------------------------------------------------------

You need Docker with the Compose plugin. Nothing else — no local Python or Node.

    cp .env.example .env
    # Edit .env and set a real JWT_SECRET:
    #   openssl rand -hex 32
    # Also set DOCKER_UID / DOCKER_GID to your own (run: id -u  and  id -g)

    docker compose up --build

Then:
    Frontend        http://localhost:5173
    API             http://localhost:8000
    API docs        http://localhost:8000/docs      (Swagger, auto-generated)
    Liveness        http://localhost:8000/health
    Readiness       http://localhost:8000/health/ready   (pings DB + Redis)

Postgres is published on host port 5433 and Redis on 6380 — deliberately NOT
the standard 5432/6379, so the stack does not collide with a Postgres or Redis
you already have installed. Containers always reach each other on db:5432 and
redis:6379 regardless. Override POSTGRES_PORT / REDIS_PORT in .env if those are
taken too.

Migrations run automatically when the api container starts. To drive Alembic by
hand:

    docker compose exec api alembic upgrade head
    docker compose exec api alembic downgrade -1
    docker compose exec api alembic revision --autogenerate -m "message"
    docker compose exec api alembic check        # detects model/schema drift

Running the checks:

    docker compose exec api ruff check .
    docker compose exec api ruff format --check .
    docker compose exec api mypy app             # strict mode
    docker compose exec api pytest

    docker compose exec web npm run lint
    docker compose exec web npm run typecheck
    docker compose exec web npm run build

3. THE FIVE SERVICES
--------------------------------------------------------------------------------

  db        postgres:16-alpine
  redis     redis:7-alpine          (job queue + cache + rate-limit counters)
  api       FastAPI via uvicorn     (serves HTTP, never makes outbound checks)
  worker    same image as api,      (makes outbound checks, never serves HTTP)
            different command: arq app.workers.main.WorkerSettings
  web       Vite dev server         (production target builds static + nginx)

api and worker share one image and one codebase but are separate processes.
That split is deliberate: a slow outbound HTTP check must never be able to
block an API request, and vice versa.


--------------------------------------------------------------------------------
4. HOW THE INTERESTING PARTS WORK
--------------------------------------------------------------------------------

### Authentication — split-token scheme

                    Access token          Refresh token
  Form              Signed JWT (HS256)    Opaque 64-byte random string
  Lifetime          15 minutes            30 days
  Lives in          Client MEMORY only    httpOnly SameSite=Lax cookie, /auth
  Server-side       Nothing stored        SHA-256 digest row, revocable

The access token is deliberately kept OUT of localStorage: anything JavaScript
can read, injected script can read too. Because it lives only in memory, a page
reload starts with no token — the SPA silently calls POST /auth/refresh, which
the browser answers from a cookie the page itself cannot read.

Refresh tokens are SINGLE-USE. Every refresh revokes the presented token and
issues a new one. Presenting an already-rotated token is treated as theft: all
of that user's sessions are revoked and a warning is logged.

Passwords are bcrypt-hashed after a SHA-256 pre-hash. The pre-hash sidesteps
bcrypt's 72-byte truncation so a long passphrase keeps its full entropy.

GitHub OAuth is wired (authorization-code flow, state stored in Redis and burned
on use). The callback sets the refresh cookie and redirects to the SPA, so no
token ever appears in a URL. Leave GITHUB_CLIENT_ID/SECRET unset and those two
endpoints return 503; nothing else is affected.

### Roles

Everything hangs off an organisation. Access is decided by the caller's
membership row, NEVER by an org_id supplied in the request (that is only ever a
lookup key).

  viewer   read the org and its members
  admin    ...plus create/edit monitors, invite members, manage channels
  owner    ...plus everything, including granting owner and revoking API keys

Non-members get 404, not 403 — telling an outsider that an organisation exists
is itself a disclosure.

### The scheduler (worker)

Every 10 seconds the worker claims monitors whose next_run_at has passed and
enqueues one check job each. Two details make this safe with more than one
worker running:

  - The claim uses SELECT ... FOR UPDATE SKIP LOCKED, so each due monitor goes
    to exactly one worker and contention never blocks.
  - next_run_at advances AS PART OF THE CLAIM, before the check runs. A worker
    that dies mid-check costs one missed data point rather than re-claiming the
    same monitor in a tight loop against someone else's server.

After an outage the scheduler catches up in a single hop rather than firing
every missed slot. A 30-second monitor unchecked for an hour runs once, not 120
times.

### Flap protection

A monitor flips to "down" only after 3 consecutive failures, so one blip does
not raise an alarm. Recovery is immediate — the first success restores "up" and
resets the counter. Both transitions are edge-triggered, which is what lets
incidents open and resolve exactly once.

### SSRF guard — the security-critical bit

A monitor is, by design, a server-side fetch of a URL the user chose. Without a
guard that is a textbook SSRF primitive: the worker sits inside your private
network and would happily fetch the cloud metadata service or an internal admin
panel on the attacker's behalf.

The guard is RESOLVE-THEN-INSPECT, not pattern matching. A hostname like
"metadata.evil.example" can resolve to 169.254.169.254, so validating the string
alone proves nothing. Every address the hostname resolves to must be public.

Rejected: loopback (all of 127/8), RFC1918 private ranges, link-local and cloud
metadata (169.254/16), carrier-grade NAT, TEST-NET ranges, multicast, reserved,
unspecified, IPv4-mapped IPv6 (::ffff:127.0.0.1), non-http(s) schemes, and
credentials embedded in the URL.

It runs THREE times: on create, on update, and again inside the worker just
before each request. The third is the important one — DNS can change between
saving a monitor and checking it, and re-resolving at execution time is what
closes the rebinding hole.

58 unit tests cover it (tests/test_ssrf.py).

### Incidents and alerting

When a monitor crosses the failure threshold the worker opens an Incident; when
it recovers, the same edge closes it and appends an automatic "resolved" entry.

A partial unique index (monitor_id WHERE resolved_at IS NULL) means the DATABASE
guarantees at most one open incident per monitor — two workers racing cannot
produce duplicates.

Notifications are QUEUED, never inline. The checker enqueues a job and moves on;
a webhook that hangs for 30 seconds cannot slow down monitoring. Delivery fans
out to every active channel, and one broken channel does not stop the others.

The one exception is POST /channels/{id}/test, which delivers synchronously
because someone configuring a webhook needs immediate feedback.

Webhook URLs are bearer credentials — anyone holding one can post into that
workspace. They are stored as given but MASKED on every read, so GET /channels
returns "https://hooks.slack.com/..." and never the secret path.

### Public status pages

GET /public/status/{slug} takes no auth dependency and returns a schema written
for that endpoint alone — never the internal MonitorRead. A visitor sees a
display name, a traffic light and a 90-day bar. The target URL, every UUID, the
assertions and the check interval all stay private. A new monitor field is
private by default rather than exposed by accident.

On the frontend the route sits OUTSIDE AuthLayout, so an anonymous visitor
triggers no session bootstrap and no call to /auth/refresh at all.

A missing slug and an unpublished page return the same 404, so the endpoint
cannot be used to discover private slugs. Monitors added to a page are filtered
through the owning org, so a guessed id from another tenant is silently dropped.

Uptime is aggregated in SQL (generate_series left-joined to a grouped count),
not by pulling rows into Python: a 90-day window on a 30-second monitor is
~250,000 rows to produce 90 numbers. Days with no checks render as explicit
gaps rather than disappearing — a monitoring outage must never masquerade as
uptime.

### Rollups and retention

A worker job aggregates each closed hour of check_results into one
rollups_hourly row per monitor, upserted on (monitor_id, hour) so a re-run after
a crash recomputes rather than double-counting.

GET /monitors/{id}/uptime reads those rollups plus the still-open hour. Measured
on 43,000 raw rows over 30 days, this cut shared buffer reads from 841 to 15.

A daily job prunes raw checks older than RAW_RETENTION_DAYS (default 30), in
batches, and only rows already covered by a rollup — so pruning can never
destroy history that was not summarised first.

### Caching and rate limiting

Public status pages (30s TTL) and uptime figures (60s TTL) are cached in Redis.
TTL-only, no invalidation: these are continuously changing aggregates where a
short staleness window is invisible. Responses carry X-Cache: HIT|MISS.

A Redis outage degrades to "slower", never "broken" — every path falls back to
computing the value.

Three separate rate-limit budgets, all Redis fixed-window by client IP:
  auth endpoints     10/min   (tightest — these are worth brute-forcing)
  public status      60/min
  authenticated writes 120/min

A Redis failure fails OPEN on purpose: losing a rate limiter must not lock users
out of signing in.

### API keys

pb_-prefixed (greppable in logs, detectable by secret scanners), shown exactly
once at creation, stored only as a SHA-256 digest. A key authenticates as an
admin of ONE organisation and is refused against any other, so POST /monitors is
scriptable from CI with no browser session:

    curl -X POST "http://localhost:8000/monitors?org_id=<ORG>" \
      -H "X-API-Key: pb_..." \
      -H "Content-Type: application/json" \
      -d '{"name":"From CI","url":"https://example.com"}'

Revoking is a soft delete, so the audit trail outlives the credential.

### Frontend

One token system. Every colour is a ROLE — surface / ink / line, plus the
reserved status colours up / down / degraded / unknown — defined once in
index.css. Dark mode is a second set of values for those same roles under
[data-theme="dark"], not a second set of components. The latency chart follows
it through var() in SVG fills.

Status is ALWAYS word + shape, never colour alone, so it survives
colour-blindness and forced-colours mode.

src/api/schema.d.ts is GENERATED from the live OpenAPI document:

    docker compose exec web npx openapi-typescript http://api:8000/openapi.json \
      -o src/api/schema.d.ts

types.ts aliases those generated schemas rather than restating them, so a
backend field that changes shape fails tsc instead of breaking at runtime.
Wiring this up immediately caught two fields the hand-written types had wrongly
assumed were always present.

8. BUGS FOUND AND FIXED DURING THE BUILD
--------------------------------------------------------------------------------

The two worth knowing about, both real and both found by testing rather than by
reading:

(a) CONCURRENT REFRESH REVOKED EVERY SESSION.
    AuthProvider's mount effect called /auth/refresh directly, bypassing the
    single-flight dedupe that only covered 401-triggered refreshes. React
    StrictMode double-invokes that effect, so two concurrent refreshes fired;
    the second looked like token reuse and triggered mass revocation. This would
    also have hit two browser tabs opening at the same time in production.
    Fixed by routing EVERY refresh through one shared promise. Verified with
    three simultaneous tab loads and zero reuse events.

(b) PUBLIC STATUS PAGE HUNG ON "Loading...".
    A failed auth bootstrap called queryClient.clear(), which aborted the page's
    own in-flight request. Fixed by only clearing when a session actually ended,
    and by moving the public route outside AuthProvider entirely.

Also fixed along the way:
  - Postgres enum types orphaned on downgrade (affected 3 migrations). An
    implicit CREATE TYPE from a column definition is never paired with a
    DROP TYPE, so downgrade-then-upgrade failed. All enums are now created and
    dropped explicitly.
  - Annotated[..., dependency] without Depends() silently became a query
    parameter, making POST /incidents/{id}/updates return 422 always.
  - Slug truncation left a trailing hyphen (caught by a test written for it).
  - date_trunc overload ambiguity with asyncpg — bind parameters arrive untyped,
    so the cast has to be explicit.
  - User.memberships was eager-loading on every authenticated request for a
    relationship nothing read.

9. GOTCHAS — READ THIS BEFORE YOU ARE CONFUSED
--------------------------------------------------------------------------------

* SELinux (Fedora/RHEL). Bind mounts need the :z label or the container gets
  PermissionError reading its own source. docker-compose.yml already sets it. If
  you add a mount, label it too.

* File ownership. Both images take UID/GID build args. Set DOCKER_UID and
  DOCKER_GID in .env to your own values (id -u, id -g) or files the containers
  write will be owned by the wrong user.

* The auth rate limiter WILL bite you while testing. 10 requests/minute per IP
  on /auth/login and /auth/register. If a test script suddenly starts failing
  after a few runs, that is almost certainly why. Wait 60 seconds.

* p95 from rollups is APPROXIMATE. Counts recombine exactly (verified:
  43,153 = 43,153). Percentiles do not — you cannot recover a true window p95
  from per-hour p95s. The reported figure is the worst hour's p95, a deliberate
  over-estimate (measured 212 true vs 216 reported) rather than a number that
  looks exact and is quietly wrong. Query raw rows for a true p95 inside the
  retention window.

* Webhook URLs accept plain http:// when ENV != prod, so a local receiver works
  in development. Production requires https://.

* example.com occasionally resolves to a TEST-NET address (192.0.2.1) depending
  on the resolver. The SSRF guard correctly blocks that. If monitor creation
  against example.com suddenly 422s, check DNS before suspecting a bug.

* The refresh cookie is scoped to Path=/auth and SameSite=Lax. If you deploy the
  frontend and API to genuinely different sites (e.g. *.vercel.app calling
  *.fly.dev) you must set COOKIE_SAMESITE=none and COOKIE_SECURE=true. Different
  ports on one host are still same-site, so lax is correct locally.

* Monitors are org-scoped via an org_id QUERY parameter, not a path segment.
  That parameter is a lookup key only — authorisation always comes from the
  caller's membership row.

10. WHAT IS NOT DONE
--------------------------------------------------------------------------------

Phase 8 is entirely untouched. Specifically missing:

  - DB integration tests. The 215 existing tests are unit-level: the SSRF guard,
    the checker's assertion logic, the scheduler's next_run_at arithmetic, role
    comparison, slugify, the notifier, rollup maths, API key hashing. There are
    NO tests that exercise auth or monitor CRUD against a real database.
  - Frontend tests. No Vitest, no React Testing Library, no Playwright. All
    frontend verification so far was done by driving headless Chrome manually
    during the build; those scripts were scratch files and are not in the repo.
  - CI. No GitHub Actions workflow. The lint/type/test commands all exist and
    pass, but nothing runs them automatically.
  - Deployment. No docker-compose.prod.yml, no platform config, no secret
    manager wiring. The frontend Dockerfile HAS a production target (static
    build + nginx with SPA fallback and immutable asset caching) but it has
    never been exercised.
  - No live deployment, so no demo URL and no screenshots in the README.

Phase 9 stretch ideas (SSL expiry checks, heartbeat monitors, multi-region
checkers, AI postmortem drafts, Prometheus /metrics, maintenance windows) are
listed in the plan and none are started.

Other known gaps:
  - Email is console-logged unless SMTP_HOST is set. No Mailhog in compose.
  - No way to change a member's role or remove a member after they join.
  - No password reset flow.
  - Incident severity is always "major" — the column and enum exist, nothing
    sets anything else.
